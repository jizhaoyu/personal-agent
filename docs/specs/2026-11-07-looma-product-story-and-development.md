# Looma 产品故事与总体开发设计

版本：设计草案 v1.0<br>
编制日期：2026 年 11 月 7 日<br>
已确认方向：以工作接续为核心，生活作为自然延伸<br>
读者：产品负责人、设计人员与接手实现的开发者

## 1 产品要成为谁

**Looma 是面向独立接单者、顾问和小工作室主理人的本地优先个人助理。它接住零散的工作信息，让用户被打断后、隔几天回来后，仍然能从正确的地方继续。**

用户不需要维护一套完整的客户管理系统，也不必把每句话整理成标准任务。Looma 先记住用户说了什么，区分事实、安排、等待与未知，再帮助用户继续处理。伙伴感来自不丢、接得上和少打扰，而不来自消息数量、人格表演或替用户猜测承诺。

**核心承诺。** 用户只需说清当下知道的部分；产品保留原始依据，持续维护事情的变化，在合适时机把下一步准备好。重要业务变化由用户核对，对外行动不默认自动执行。它不是“保证所有事情都能自动完成”的全能代理。

**主次关系。** 工作是第一条完整价值链：沟通记录、项目继续、条件意图、材料准备、完成与停止。生活保留随口记录、事实与个人待办，复用可靠存储、时间理解和提醒能力，但不与工作争夺第一阶段开发资源，也不将生活资料默认带入客户工作。

本文是后续研发的总设计基线，不是实现完成声明。已确认的是产品方向；新增结构、交互和分期仍需本次文档评审。研究中出现的技术只作为设计输入，不意味着必须引入对应框架、模型或服务。

**成功的衡量。** 一位用户重新进入项目后，能迅速理解当前情况并继续处理；少重说一遍，少翻一轮聊天，少纠正一次重复事项。记录数量、代理数量和调用次数都不是主要成功指标。

## 2 产品故事从一件没有说完整的事开始

以下为设计用虚构故事，不是真实用户访谈或已实现功能演示。主角林安是一名独立设计顾问，同时服务三个客户，主要使用 Windows 电脑，外出时用 Android 手机记事。

**第一天 不必整理完再记。** 林安刚结束电话，赶着去下一场会议，写下：“陈总的星河官网项目，预算还没定。等他把首页素材补齐，我再发新版方案。”Looma 先保存原话，再整理归属、等待和附带条件的下一步。预算保持未知，不用旧报价填空；没有具体时间也能留下这件事。林安核对重要变化后离开，不必补完一张项目表单。

**第二天 改口不是另起一条。** 林安补充：“星河的素材先不用催，陈总说下周整理。新版方案等他确认品牌色之后再发。”产品展示条件从“素材到齐”改为“品牌色确认”，而非多造一条冲突待办。两段原话仍可追溯；客户预计“下周整理”也不自动变成林安的固定闹钟。

**第四天 回来就知道从哪里继续。** 林安打开项目，首先看到当前安排、等待客户和最近变化：现在等的是品牌色确认。他不用从四天前的聊天开始翻，也不会被过时的素材条件催促。每条结论可以查看依据；已删除的历史明确显示不可用，摘要不冒充原话。

**条件成熟时 准备好而不是擅自发出。** 林安记录：“陈总确认用深蓝色，星河官网按这个推进。”产品核对后提供准备入口。林安点击生成，得到标有来源、待补信息的方案说明与材料检查清单。Looma 不填未知预算、不发送邮件。他编辑并自行发送，再记录“星河新版方案已经发了”，原意图结束，不重复提醒；这也不代表整个项目已经完成。

## 3 用户为什么会持续使用

### 核心用户与边界

首要用户是需要跨天维护多个客户项目、但不想专门运营 CRM 的独立工作者。其痛点是信息分散、上下文切换、等待事项遗忘，以及每次回来都要重建背景。小团队可作为后续使用场景，但首版不引入多人权限、共享任务分配或组织级审批。

生活场景是工作主线的自然延伸：用户可以顺手记个人安排和生活事实，不必换一种输入习惯。产品不因此扩展为健康诊断、财务顾问、社交陪伴平台或自动消费代理。

### 四个持续价值

**省下组织信息的力气。** 可以先说半句、先记原文、稍后再整理。产品不以反复追问证明自己聪明。

**省下重新理解的时间。** 进入一个项目先看到当前情况及下一步，而不是所有历史或一堆统计指标。

**省下准备下一步的重复劳动。** 在信息足够时提供草稿和清单；信息不足时保留缺口，而不是编得完整。

**保留控制与退出能力。** 用户可以更正、撤销、取消、删除和停止建议。自动整理的便利不以丢失资料控制权为代价。

### 产品不做的事

首个演进周期不做自动发邮件、付款、下单、跨账户写操作、持续录屏录音、自动改写应用代码、跨设备实时同步或通用多代理平台。它们不是永久否定的方向，而是当前闭环之外的独立项目。不能为了接入这些能力让可靠记录依赖服务器在线。

## 5 把研究启发变成产品决定

研究输入沿用《Personal Agent 技术成果与 Looma 产品启发》2026-11-07 版本。本节是设计取舍，不声称外部系统已证明 Looma 的用户收益。

**采用分层记忆思想，不照搬整个框架。** 原始事件、已核对当前状态、派生摘要和交互偏好分别维护；先复用本地仓储与查询，首版不引入向量库、图数据库或专用记忆模型。需要召回优化时再做有基线的实验。[Anthropic memory](https://www.anthropic.com/research/components-of-agent-memory)

**采用条件与时机判断，不复制全天感知。** 条件意图只由用户输入、用户确认的业务变化和显式检查触发。记忆相关不等于立即通知；已取消、过时或已提醒的候选必须停止。[MemoProAgent](https://arxiv.org/abs/2610.22671v2)

**采用单一写入所有权，不马上做多端服务。** 桌面窗口、后台任务和通知都读取同一任务身份及版本；一次操作的重试不能产生第二次提交。跨设备同步留到另行设计身份与冲突策略时。[Hermes release](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.0)

**采用场景化协助偏好，不无限扩大个性化。** 用户的明确设置可以影响表达长度、是否展示建议和何时主动联系；某个客户的偏好不影响全部客户。重要事实核对不能仅凭“我喜欢少确认”被取消。[MemPABench](https://arxiv.org/abs/2610.30485v1)

**采用可审查产物，不扩张无人执行。** 下一步输出先是方案说明、材料清单或会前简报草稿；在证据不足时说明缺口。参考持续代理方向，但首版不使用外发权限。[dots](https://openai.com/index/introducing-dots/)

**采用失败回放，不在线自我改写。** 纠正、撤销和误触发进入经脱敏的评估样本；候选规则要在留出集通过才进入正式版本。不得把用户正文自动汇出或让生产代理自行修改规则代码。[Reglos](https://arxiv.org/abs/2611.06049v1)

## 6 连续旅程和信息架构

### 工作台负责接住与继续

保留“记一条工作进展”作为主入口。桌面端以输入区为主、摘要为辅；窄屏先输入后摘要。全空时一条提示即可，有内容再展开相应分组。未完成草稿优先恢复，不能被示例、模式切换或新建议覆盖。

再次进入时，可以从未完成草稿、今日行动或最近项目继续。系统不以自动弹教程、强制建项目或让用户选记忆类型作为入口条件。

### 项目负责解释当前情况

项目页首先回答当前状态、下一步、等谁和最近发生了什么。预算是辅助事实，不做最大字号仪表盘。每条结论可展开依据；“当前保存值”和“客户已确认”必须区分。跨页加载不能把当前窗口误当全部记录。

项目行动维护执行进度；工作提醒管理已安排或待补时间的待办。两者有业务关联，但产品不展示为两个需要用户重复录入的系统。完成或取消后相关视图刷新，以实际事务结果为准。

### 核对页只展示需要用户决定的内容

顶部概述新增、更新、移除的内容，正文优先显示差异和阻塞项；普通编辑按需展开。客户、项目、预算用留白和细线分隔，下一步适度强调。窄屏确认入口保持可触达，不用连续彩色密集小卡表现每个字段。

明确规则是：有歧义时解决归属；有冲突时选择保留值；没设时间仍可保存；没有重要变更时不制造整页确认。任何自动保存捷径也必须保留结果回执与来源。

### 下一步准备贴近项目出现

可用建议在对应项目内展示，不新建一条与所有任务竞争的消息流。每次至多突出一个最相关的准备动作，其余按需展开。用户可忽略本次或关闭此类建议；精确闹钟和可选工作建议分别管理。

生活保持独立查看与上下文边界。小精灵和陪伴元素可以保留，但状态反馈应服务于“已记下、需要核对、可继续”，不遮挡工作信息或靠持续动画吸引注意。

## 7 用户故事与验收闭环

下列故事是总体范围基线；编号用于开发与测试追踪。每项都检查真实最终状态，而非只检查回复文本。

**US01 零负担记录。** 作为刚结束沟通的用户，我要先留下不完整原话。验收：无预算、无时间、无项目时也能可靠保留；存储失败仍保留输入并报告未保存；只有存储实际成功才显示本机已保存。

**US02 必要的归属确认。** 当两个客户或项目同名，我只需做一次明确选择。验收：不猜实体；选择后沿用唯一身份；一次输入涉及两个项目时分别建立候选，不整段塞给同一项目。

**US03 修改同一件事。** 我说“改成周四”时，要修正原事项。验收：有唯一上下文才更新，否则展示短选择；事务后未完成事项不增一条；旧提醒失效，原表达与改动来源可追溯。

**US04 跨日继续。** 我回来时要看到仍有效的安排。验收：关闭重开后草稿与当前状态可读；摘要不依赖新增模型请求；能查到等待、未定和原文；已删除依据明确不可用。

**US05 保存条件意图。** 我能记录“品牌色确认后再准备方案”。验收：条件不被擅自补成固定日期；绑定唯一项目和明确条件；条件不清时只保留草稿，不启动后台判断。

**US06 条件成熟后准备。** 对应项目的条件被确认满足后，我能选择准备下一步。验收：只匹配已绑定对象；先检查完成、取消和版本；重复事件不产生重复建议；生成前由用户点击。

**US07 产物可核对。** 我能编辑一份有依据的方案说明。验收：产物带来源和版本；未知预算标为待补，不编造附件存在；源记录变化后标为待重检；取消生成不把半成品说成成功。

**US08 停止与撤回。** 我说“不用了”或完成事项后，不再被旧安排催促。验收：完成、取消、暂停可区分；暂停不等于完成；恢复后基于当前版本重新判断，不重新投递旧建议。

**US09 控制协助方式。** 我可以关闭工作建议，但继续接收自己设的闹钟。验收：两类设置独立；关闭后不再主动突出新建议；原文与工作状态仍保留。

**US10 生活不污染工作。** 我能用相同习惯记生活。验收：个人事实不误建项目行动；工作查询和模型上下文不默认包含生活资料；跨空间不明确时先保留再澄清。

## 8 总体技术架构

**架构选择是渐进增强，不重写现有产品。** 保留 React 界面、现有本地 Repository、桌面与 Android 桥接。新增能力以本地应用服务接入，不创建新的聊天后端或独立事实库。

数据流为：输入与草稿持久化 → 当前空间与上下文解析 → 确定性路径或模型候选 → 实体和版本校验 → 必要核对 → 原子提交 → 更新接续投影 → 条件评估 → 用户选择准备产物。旁路可以查询和导出，但不得跳过写入校验。

**界面层。** 展示真实持久化状态、候选、依据和阻塞原因；保存草稿不依赖模型完成。组件不直接写原生数据库，不在展示渲染过程中执行外部动作。

**理解层。** 简单且明确的指令优先复用本地路径；含糊指代、多事项与复杂纠正可调用模型。模型只返回结构化候选、来源片段和对象引用，不能直接执行 SQL、创建未经校验的实体引用或自报执行成功。

**应用服务层。** 复用现有 capture、personalAgent、todos 和 projectContinuation 的职责。补充条件意图评估和产物准备服务；不将它们继续堆入单个页面组件。它们通过 Repository 查询、提交和订阅变更。

**本地仓储与派生层。** 业务事实及事件是可信状态，摘要、候选建议和检索索引是派生数据。派生内容可重建，不反向覆盖已核对事实。所有新记录受工作分区、版本和恢复身份约束。

**平台层。** Windows 为首个完整验收平台；Android 保持已有能力，新增前台流程在后续阶段单独验收。浏览器仅承担本地与前台能力验证。窗口隐藏、应用退出、设备关机不是同一种后台状态。

**模型层。** 沿用用户设置与已有连接方式，不在文档中锁死新模型或新增依赖。每个请求记录用途、开始时间、请求身份与结果类别；凭据不进入业务记录、日志和导出。

## 9 数据与接口的最小增量

以下是建议新增的内部契约，不是已经存在的公共 API。具体 TypeScript 名称和迁移编号由分期实施文档给出，但实体职责、生命周期和写入边界按本节锁定。首版不发布外部 API。

**原有事实保持原位。** Engagement、ProjectTaskItem、FollowUpItem、CaptureDraft、ProposedChangeSet、ClosureRecord、CommittedChangeEvent 与 TodoRecord 继续承担现有职责，不创建一个包罗万象的 AgentMemory 实体替代它们。

**ConditionIntent。** 记录一个项目内的条件安排：身份、work 空间、项目 ID、行动描述、结构化条件、状态、来源引用、版本和更新时间。条件首版只支持“已绑定等待项被用户确认为收到”和“用户确认某条件满足”；任意自然语言可以保存为待澄清草稿，但不作为可执行条件。

**状态定义。** draft 只存候选；watching 表示条件已核对、等待后续；ready 表示条件成立、可准备；paused 暂不评估；completed 和 cancelled 是停止状态。条件或行动修改产生新版本。触发到 ready 不自动创建第二个 ProjectTaskItem；如要创建独立行动，走既有核对与来源关联。

**ArtifactDraft。** 首版仅支持方案说明、材料清单、会前简报三种文本产物。保存类型、项目、关联意图、内容、来源快照版本、状态与生成时间。准备由用户点击启动；ready 仅代表草稿可看，绝不代表发出。相关事实变更后转为 needs_review。

**辅助契约。** SourceRef 至少能定位空间、记录种类、实体或原文 ID、当时版本。内部 EvaluationRun 保存输入版本与请求身份；重复投递同一意图版本和触发事件只产生一次结果。全局协助设置记录关闭建议与静默时段，工作和生活分别设置。

**服务输入输出。** 条件评估输入为已提交事件与当前仓储身份，输出为未匹配、候选变化或失效原因；产物准备输入为唯一项目、产物类型、来源版本，输出为草稿或明确失败。二者不得以自然语言回复替代结构化结果。

## 10 版本恢复和失败处理

**迟到结果。** 请求开始时记录仓储恢复身份、项目版本和意图版本。返回时重新比较；身份变化、用户修改或取消后，旧结果不提交为当前产物。需要时可提示重新生成，不静默回滚用户新输入。

**写入原子性。** 条件状态变化、相关事件与去重记录通过既有事务边界协调。不能先显示完成再补写来源。结果未知时进入核查状态，不盲目再次提交。

**离线和模型失败。** 已成功保存的原文不受影响。网络超时、非结构化输出、无效字段或引用不存在时，保留可继续的草稿并明确失败。用户可仅保存原文；不自动无限重试。生成支持取消，取消只作用于本次请求。

**恢复与迁移。** 新记录的存储种类须同时纳入桌面、浏览器、备份导入导出和原生桥接的允许范围；新增集合默认空。升级前保留可验证备份；升级失败不得把旧库覆写为默认空库。旧版不认识新增格式时拒绝导入并提示版本要求，不静默丢弃条件与产物。

**来源删除。** 对象删除使引用失效，相关建议停止展示或转为待检查；删除原文后，不从事件副本、摘要或产物还原原话。真实删除与保留审计元数据分别处理，不能用“追加日志”绕过删除语义。

**跨平台一致性。** 同一输入与固定时钟在 SQLite、IndexedDB 产生等价的业务结果；原生调度由平台能力单独判断。Android 在后台或进程终止后不能运行的功能，不得在界面承诺已经持续执行。

**时间边界。** 保留原日期表达、可解析日期、具体提醒时刻和时区语义。客户预计、用户截止与主动建议窗口不能复用同一个字段。仅知道“周四前”时不擅自变成周四某时的精确闹钟。

## 11 主动性与记忆维护的约束

### 第一版怎样判断值得展示

只在用户确认保存、新增关联进展、用户打开相关项目或主动检查时评估。用户打开工作台的检查是本地派生，不额外发起模型调用。无新证据、来源失效、对象不唯一或处于停止状态，一律不产生可执行建议。

首版工作建议只在应用内展示，不主动发送系统通知；用户设定的精确提醒继续走现有提醒通道。这样可以先检验建议是否有用，再独立评审通知权限、打扰预算和后台执行。

同一项目只突出一个 ready 建议，同一意图版本只突出一次。用户忽略本次后，该版本不再次突出；只有新的相关事件或用户主动检查才可重新呈现。关闭工作建议时不取消用户自己的闹钟。

### 记忆维护何时开始

首个周期只维护来源链接、当前有效版本、明确状态和用户设置，不推断隐含的人格或交互偏好。可以生成项目摘要，但摘要是派生内容，不能成为没有来源的新事实。

后台 dreaming、学习型记忆和复杂图检索都放入后续实验。实验默认关闭、需用户选择并有调用预算；输出先作为待审查材料。不得在生产环境自动改代码、部署新规则或向外汇出用户记录。

**边界原则。** 用户反馈可以改变表达习惯和建议展示，但不能让系统把猜测当已核对事实。对外写入、跨空间引用和凭据使用仍属于独立能力，不能由一句泛化偏好隐式开启。

## 12 分期开发和退出标准

不承诺未经估算的上线日期。按可验收闭环推进，每期通过后再扩展。已有功能先审计和补缺，不重复开发。

**M0 建立可复现基线。** 对应 US01 至 US04、US08、US10。清点已有草稿、接续、来源、改期取消和提醒链；固定失败样本与发布测试方法。交付现状清单、回归集和能力矩阵。退出标准：无数据丢失、错误跨空间引用、重复提交及误完成的阻断样本；失败项可重现且不被平均分掩盖。

**M1 打通工作接续闭环。** 优先 US01 至 US04。以现有项目详情和工作台为基础，验证第一次输入到隔日继续的完整路径；清理重复入口与不真实的状态提示。退出标准：隔离数据下关闭重开可继续；用户能从摘要定位来源；不增加模型调用来维持首页摘要。

**M2 形成第一类条件意图。** 对应 US05、US06、US08、US09。只支持本文件约定的明确条件类型；完成存储、核对、版本、去重、停止与恢复。退出标准：改条件后旧条件不触发；重复事件不重复建议；完成取消后停止；不依赖后台常驻。

**M3 准备一种有用的产物。** 先做方案说明，再按同样契约扩展材料清单、会前简报。对应 US07。退出标准：未知信息不编造；原文和字段变更使旧稿待重检；取消和失败如实反馈；不具备外发权限。

**M4 平台和真实试用。** 对 M0 至 M3 的最终 Windows 发布包和实体 Android 前台流程分别验收，再进行 5 人 7 天试用。只发布已达到平台标准的能力；不能用浏览器通过代替安装包和真机验证。

远期候选单独立项：只读日历连接、显式用户偏好记忆、多设备同步、后台主动通知、外部动作。它们不作为 M0 至 M4 完成的前提。

## 13 验收和度量方式

### 自动化先验证是否做对

建立至少 200 条单轮语句、40 条连续轨迹，覆盖同名客户、纠正否定、条件变更、取消暂停、来源删除、存储失败、模型迟到和备份恢复。样本按用户或项目分开发集与留出集；时钟、模型、工具和初始数据固定，不偷看未来信息。

| 验收层 | 必测结果 |
| --- | --- |
| 规则和服务 | 意图与实体匹配、条件状态转换、时间边界、去重和取消 |
| 仓储和恢复 | 原子提交、版本拒绝、SQLite 与 IndexedDB 等价、备份往返 |
| 浏览器交互 | 桌面与 390px 输入核对、展开编辑、草稿保留、来源和键盘焦点 |
| Windows 发布包 | 真实安装或便携目录启动、重开、通知定位、退出能力和失败恢复 |
| Android 真机 | 中文输入法、前台保存恢复、权限变化、通知触达与点击后的真实状态 |

所有严重错误样本必须 100% 通过才能进入试用：原文丢失、误完成、错误客户预算、跨空间泄露、重复业务提交以及取消后执行。其他识别准确率分场景报告，不用一个总准确率遮盖问题。

### 真实试用验证是否值得留下

5 位目标用户连续使用 7 天，重点观察：跨日回来时理解项目要多久、重复交代几次、每次记录修正几步、建议是否有用、是否产生额外负担。用户不必交出完整客户正文；可用脱敏任务和主动提交的反馈。

首轮产品门槛建议为：至少 4 位用户能不看教程完成核心旅程，并在后续日子主动再次用于工作接续；至少 4 位能借助继续卡说明下一步而不重新翻原始聊天。样本很小，结果只决定是否继续试用，不外推留存率或市场规模。

记录模型调用、token、P50/P95 延迟和失败类别；派生工作摘要不新增模型调用。产物生成的等待体验在真实测量后设定目标，不在没有基线时编造毫秒承诺。

## 14 实施交接和兼容约束

**进入开发前的交付物。** 每一期补一份实施清单：当前实现与目标差异、涉及模块、迁移和兼容策略、故事编号、失败路径、测试命令及发布证据。总文档负责决定做什么和边界，实施清单负责当时具体文件与步骤。

**代码责任。** 页面只处理交互；业务判断进应用服务；持久化和幂等进仓储与事务；平台行为进现有桥接。新增依赖不是默认选项；只有基线证明现有能力不足才评估引入。不能把研究框架直接接入所有读写路径后再补隔离。

**迁移责任。** 新实体、导出格式或原生命令变更必须同步测试；备份含不含条件和草稿产物须明确。不可恢复的破坏性迁移不能作为本设计的隐含步骤。正式数据操作前单独核对目标和回退材料。

**发布责任。** 新条件与产物功能使用本地开关分期启用，已有流程可用。开关关闭停止新增评估，不删除既有记录；有进行中请求时仍通过版本检查防止迟到写入。关闭功能不是可降级打开新库的保证，程序版本兼容另测。

**技术债控制。** 不保留旧入口只为让过时测试通过；测试应验证用户实际可见入口和真实业务结果。需要调整旧契约时同时说明兼容影响，不重置用户未提交改动。

本文件是审阅用总体设计草案。完成文档不表示启动了 M0 或完成任何迁移、模型试验和真机验收。用户认可总设计后，再按 M0 的现状审计结果细化第一期实施计划。

## 15 决策记录与阅读索引

**ADR01 用户和主线。** 已确认以独立工作者的工作接续为核心，生活自然延伸。拒绝双主线同时扩张，避免有限资源分散。

**ADR02 演进方式。** 基于现有项目、草稿、回执、来源和提醒增量建设，不重做成另一套代理平台。

**ADR03 主动性。** 首版文本事件驱动、应用内建议、用户点击生成；暂不持续感知、系统主动推送和无人外发。

**ADR04 记忆。** 原文和事实分离，派生摘要可重建；先规则与结构化查询，不默认引入图数据库、向量库或新模型。

**ADR05 执行。** 模型提供候选，本地版本与事务决定提交；完成、取消和删除都能让旧结果失效。

**ADR06 平台。** Windows 先完成闭环，Android 单列前台与提醒验收；不做跨设备实时同步的隐含承诺。

**ADR07 成果。** 以可核对草稿帮助用户推进，不以通知数量、模型能力宣传或代理数量衡量价值。
