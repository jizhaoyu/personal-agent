# Looma 首轮优化计划：可信的单人客户跟进闭环

状态：用户已批准并要求实施。日期：2026-10-26。本文固化确认计划；实际执行和验证证据另记于实施记录，不能将计划状态理解为完成状态。

## 1. 已确认的目标与商业定位

面向**独立接单者、顾问和小工作室主理人**，交付可以承载真实案例的本地单人试用版，跑通：

**文字或粘贴沟通记录 → 变更预览 → 一键确认 → 客户项目与待办更新 → 到期提醒 → 可审核的沟通纪要。**

生活态继续保留，与工作态严格分区。首轮优先验证整理效率、记录可信度和重复使用，不接入账户、支付或团队云协作。

商业优势应围绕以下可验证结果建立：

| 潜在优势 | 首轮如何落实 | 如何证明 |
| --- | --- | --- |
| 减少录入和整理负担 | 从一段沟通中提出客户、金额、日期和行动变更，集中核对 | 与手动整理同一案例的耗时比较 |
| 记录持续可用 | 项目、待办、来源和变更历史相互关联，支持修正与撤销 | 连续使用、重启恢复、重复跟进场景 |
| 内部记录形成交付价值 | 从用户选定的信息生成待确认纪要，支持文本和 PNG | 纪要准备耗时、重复导出与实际采用情况 |
| 本地使用与数据控制 | 基础流程离线可用，模型增强由用户主动开启，备份不含凭据 | 离线、隔离、备份恢复与网络请求检查 |

**“全球没有该产品”不能作为现阶段的商业事实。** Dex 已提供对话式联系人维护，Tana 已提供语音结构化记录，folk 已提供 CRM 字段自动更新。它们证明需求存在，也说明单个功能难以形成独占优势。[Dex 官方文档](https://getdex.com/docs/ai/voice-mode)、[Tana 官方介绍](https://outliner.tana.inc/voice-memos)、[folk 官方更新](https://www.folk.app/changelog/ai-fields)

截至本次检索，Looma 值得验证的是这些能力在特定场景中的组合体验。即使没有完全同构的产品，也同时意味着市场教育成本；后续应靠可靠流程、领域模板和用户习惯积累优势。

## 2. 核心设计与接口约定

**统一变更管线。** 将现有“解析后立即写库”拆成候选解析、校验、提交和撤销。工作态聊天、卡片编辑、阶段推进和待办勾选共用提交入口，后台记忆提取也不得绕过确认。

- 新增 `ProposedChangeSet`、`CommittedChangeEvent`，记录来源消息、所属空间、基础版本和字段前后值。
- 提供 `propose`、`validate`、`commit`、`undo` 接口。解析不产生持久化副作用；提交成功后才显示“已记录”回执。
- 一次输入的变更作为一个批次提交，全成或全败；重复确认同一候选不重复写入。
- 旧预览遇到新编辑时要求重新核对，避免覆盖后续修改；按时间倒序逐步撤销最近变更。
- 人物不明确、金额单位缺失、否定或假设语义不清时保留原文并提示核对，不猜测成交状态或补全金额。

**最小业务模型。** 以“客户合作项目”和关联待办支撑首轮流程，同一客户可以有多个合作项目。预算允许未知；待办保存原始日期表达和确认后的日期。内部备注与可外发摘要分别存储，外发内容不直接复用原始聊天。

**版本化本地存储。** 新增 `AppSnapshotV3`，包含明确的 `life`、`work` 分区、各区版本、业务数据和变更历史；普通设置不含 API Key。所有仓储访问强制指定空间，正常更新只能修改当前分区。

- 整个快照经校验后单次写入；写入失败时保留原数据，界面不得显示成功。
- 禁止关键词触发跨区写入，关闭工作量扣减生活精力的桥接。
- 异步请求固定所属空间，切换模式后旧响应不得覆盖当前界面。
- 产品文案使用“本地逻辑分区”，准确说明当前能力；业务数据本轮不宣称已加密或具备物理隔离。

## 3. 分步实施与交付

1. **固化设计与修复基础运行。** 将已批准设计和实施清单落入项目规划文档；记录现有基线。修复生产启动仍依赖开发服务器的问题，统一启动脚本与 README，使构建后的桌面程序能直接加载本地页面。

2. **完成存储迁移与核心变更闭环。** 先建立版本化仓储，再接入预览、修改、忽略、确认和撤销。迁移只读取实际存在的旧数据，不把 getter 自动生成的示例当成真实记录；新工作区为空，示例通过明确入口体验。旧 CRM 自由文本按内部资料保留，未关联任务不自动猜测项目归属。

3. **接入受控模型增强。** Windows 桌面版通过主进程保存凭据并发送请求，使用当前 Electron 版本支持的 `safeStorage` API；安全存储不可用时不明文落盘。保存后界面只读取连接状态，不回读 Key。用户主动启用增强后，仅发送当前输入和选中项目的必要字段，默认不附加内部备注、其他项目或另一空间的数据。[Electron safeStorage 文档](https://www.electronjs.org/docs/latest/api/safe-storage)

   本轮支持 OpenAI 兼容接口与 Ollama。模型返回的内容必须经过结构、字段和目标实体校验，再进入同一候选预览。请求设置超时与取消，失败时明确提示并保留原文；重试不重复提交业务变更。浏览器预览只提供本地流程。

4. **完善工作台、提醒与外发纪要。** 工作台集中显示客户合作项目、下一步行动、今日和逾期待办。日期按 `Asia/Shanghai` 解释，并在预览中展示绝对日期；只有日期而没有时刻的待办，默认当天 09:00 提醒，可在确认时修改。桌面运行时检查到期事项，重开后汇总遗漏；系统通知默认隐藏客户细节，通知不可用时仍保留应用内提示。

   新增独立的 `AlignmentDraft`，默认标题为“沟通纪要草稿／待对方确认”。仅从用户选定的项目和明确选择的字段构造，内部备注不进入草稿，预算默认不选入。用户编辑、预览后可复制文本或导出 PNG；未有确认依据的内容不标为“已达成共识”或“我方承诺”。

5. **补齐恢复与统一商业材料。** 备份覆盖两区业务资料、自定义卡和变更记录，导入先完整校验，再原子替换；无效文件不得部分覆盖。凭据不进入备份、日志或事件；旧明文 Key 仅在安全迁移成功后移除。

   同步更新 README、商业计划书、PRD、技术架构和 Word 汇编，统一“已实现、待验证、后续路线图”的边界。删除无来源的留存率、零获客成本和确定毛利表述，现有价格保留为试价假设。Word 更新后执行渲染与逐页检查。

## 4. 验证与验收

### 自动化检查

- 使用现有 TypeScript 与 Node 内置测试能力验证解析、校验、提交、撤销和迁移，不新增测试框架依赖。
- 固定案例覆盖多金额、多人物、不同单位、相对日期、否定句、假设句和更正句；重点包含“预算 300 元”“还没成交”“预算从 8 万改为 12 万”。
- 验证重复确认、过期预览、写入失败、撤销、重启恢复，以及坏备份导入后原数据不变。
- 检查工作态请求、查询、日记、回执和导出均不读取生活数据；发送中切换模式不串台。
- 使用受控模型响应验证正常返回、格式错误、超时、失败与重试；没有真实模型凭据时，明确区分模拟验证和真实服务验证。
- 运行类型检查、相关测试与生产构建，读取实际输出后再报告结果。

### 实际运行验收

- 浏览器完成“输入 → 预览 → 修改 → 确认 → 卡片更新 → 撤销 → 刷新恢复”全过程。
- Electron 验证构建后独立启动、凭据保存、模型连接状态、到期通知和重开汇总。
- 检查纪要文本和 PNG 的内容、长文本布局及内部字段排除情况。
- 全新用户不出现虚构客户、报价或账单；演示入口与真实工作区有明确区分。

### 商业试用验证

工程验收完成后，由用户安排 5 名目标用户试用 7 天，不由代理自行联系外部人员。每人先用原有方式、再用 Looma 整理同类真实案例，记录整理耗时、修正次数、重复使用、纪要采用情况及付费意愿。

初始验证目标为：多数试用者无需指导完成首次确认；整理耗时较原方式下降约 50%；至少 3 人在一周内跨 3 天重复处理真实事项。这些是实验目标，不能提前写成产品成绩。

## 5. 已确认边界与实施默认值

- 本轮交付真实案例试用版；Windows 桌面提供完整能力，Web 提供本地预览。
- 输入限文字与粘贴记录；语音、截图识别、任意结构造卡、云同步、支付、团队权限和退出后的后台提醒留待后续。
- 生活态保留，仅处理必要的隔离、存储迁移和恢复兼容问题，不扩展生活功能。
- 复用现有 React、Electron、TypeScript 和导出工具，首轮不迁移 SQLite，不建设官方模型服务。
- 用户在当前空间主动输入的原文仍属于该空间。“未跨区写入”不等于自动识别并清除了原文中的所有隐私。
- 本轮不自动发送客户材料、不发布、不远程推送；外发材料由用户审阅并自行使用。
