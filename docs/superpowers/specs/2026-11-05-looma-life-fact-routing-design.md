# Looma 生活态：事实与行动分流设计

## 目标与边界

明确发生的事实照常记录，明确的待办走现有待办链路；未发生、未确认、转述、假设或无法确定的部分只保留原话，不入账、不改待办、不弹确认、不追问。同一句有独立、明确的事实或行动时，只处理明确的部分。

本轮不重做界面，不改工作态、资料库格式或通知机制，不给 APK 新增远程模型连接。保留待办唯一目标、版本检查及原话留存。非整杯饮水沿用现行换算口径，与「3 杯被记成 1 杯」分开验收。

## 方案选择

- 继续在各入口补正则：改动小，但待办和记账仍可能得出不一致结论。
- **离线优先，共用一套分流（已选）：**先区分已发生事实、明确行动、仅保留原话，再调用现有写入服务。
- 远程模型拆解后本地验证：适合复杂输入，有网络和成本依赖，只在新样本上证明有收益时考虑；模型不直接写入。

## 行为与数据流

1. 由现有入口先保存整段原话。新增纯函数，对生活态片段给出分流和原文范围，保护千位金额、引号和否定范围。先确认是否实际发生、是否属于用户，再提取字段。「退款39元，还没到账」不拆成已发生的收入；后面独立、明确的午饭支出仍可记录。
2. 同一笔已确认的金额事件只选收入、支出或心愿存入中的一个类型。不同的明确事件可以分别写入，不能仅凭金额相等去重。金额、类型或归属不明不提交。复用现有原子提交、来源 ID 和去重；混合输入不假定账本与待办跨服务原子，重试不得重复已写入的事项。
3. 待办只消费明确行动或通过既有目标、版本、时间校验的跨轮变更。普通未来计划仍需有可辨识的行动；过去事实或普通陈述不能仅因出现「今天」就建待办。
4. 生活态待办和生活记录入口共用分流，移除仅针对生活态的重复判断；工作态保留原逻辑。预计涉及生活态编排、待办分析和生活记录解析。

## 验收与换路线条件

- 冻结原 204 条成品用例。9 条误入账、4 条多写账目类型、11 条误建待办逐条复测；这些分组可能重叠，不简单相加。明确提醒保持 14/14，既有待办状态专项中的 14 条不写入用例仍应不写。分别记录错写、漏写、误弹和重复，不能靠全部不写来通过。
- 冻结新说法再开修，覆盖否定后接真支出、同金额不同事件、退款与转账、活动完成与未来计划、记账与提醒混合、模糊目标和重试。以最终记录和确认卡为准，而不是只看意图标签。
- 用 gpt-6.1-sol 对同一批合成用例做隔离对照，不发送真实账本、不在文件中存储密钥。若本地路线在新用例上仍反复漏记或错分，换成「模型按原文片段生成结构化候选，再由本地校验」的小范围实验；只有在新样本上不增加错写且能恢复明确应写的输入，才考虑接入桌面模型入口。
- 通过本地回归后，验收 Windows 便携成品的实际账本、浮卡和重启恢复；在专用雷电测试实例中验收签名 APK 安装、代表性口语、提醒触发及点击跳转。雷电验证不等于物理手机；ADB 不通或模拟器权限受限时，具体项目标为未验收。
